# 上海科技大学2026视觉技术方案 — 整体对比分析

> 对比对象：当前实现 (hfut_rm_auto_aim_ws v2.0) vs 上海科技大学2026开源技术方案
> 来源文档：tmp/上海科技大学2026视觉技术方案开源.docx（核心技术整理见 tmp/视觉技术方案核心技术整理.md）

## 一、当前实现的优势

### 1. Max-Entropy UKF 装甲板关联机制

当前实现使用解耦 UKF + 最大熵面板去歧义 + 跳跃绑定（jump binding），专门针对 RoboMaster 四面板机器人建模（`yaw = k·π/2 + delta`），通过熵最小化来消除面板歧义。

参考方案使用马氏距离进行装甲板匹配，属于传统数据关联方法。当前实现在此之上做了专门化设计，天然适合多面板目标场景，是独特优势。

关键代码：
- `max_entropy_tracker/filters/dual_radius_spin_ukf.cpp`
- `max_entropy_tracker/binder/core/binding_fsm.hpp`

### 2. g2o Bundle Adjustment 位姿精修

参考方案的 "CornerRefine" 是在 2D 图像层面做角点精修。当前实现在此之上还有 g2o 图优化层，用李代数对 yaw 做单变量 BA 优化（LM 求解器 + Huber 核），在 3D 几何层面进一步降低位姿误差。这是参考方案没有提及的额外优化层。

关键代码：
- `armor_detector/src/ba_solver.cpp`
- `armor_detector/include/armor_detector/graph_optimizer.hpp`

### 3. 一体化 Pipeline 零延迟架构

参考方案讨论流水线并行时仍停留在"采集/推理/后处理"的多线程拆分。当前实现直接将 tracker → selector → controller 合入单个 ROS 节点 (`gimbal_pipeline`)，消除两跳 ROS 话题通信（tracked_robots、selected_target）的序列化/调度延迟。这个架构层面的优化参考方案没有提及。

关键文件：
- `rm_bringup/launch/bringup_pipeline.launch.py`
- `gimbal_pipeline/`

### 4. MPC 实现更完整

参考方案提到了 TinyMPC/ADMM 但未展开细节。当前实现包含：
- qpOASES QP 求解器
- B_d 矩阵延迟映射（精确建模控制延迟）
- 机动自适应 Q/R 权重
- 基于命中概率的状态相关加权
- FOV 软约束（带松弛变量的 QP 扩展）
- 滑动窗口 RMS 数值归一化
- Hessian 自适应正则化

关键代码：
- `gimbal_pipeline/include/gimbal_controller/mpc/gimbal_dynamics_model.hpp`

### 5. 多推理后端 + 异步调度

参考方案只提到 YOLO-Pose。当前 NN 检测器支持 ONNX Runtime / TensorRT / OpenVINO 三后端，并提供 SYNC / ASYNC_LATEST / ASYNC_BATCH 三种调度模式。

关键代码：
- `armor_detector_nn/include/armor_detector_nn/onnxruntime_backend.hpp`
- `armor_detector_nn/include/armor_detector_nn/tensorrt_backend.hpp`
- `armor_detector_nn/include/armor_detector_nn/openvino_backend.hpp`

### 6. IMM 交互多模型

参考方案用了 KF → EKF → IESEKF 的单模型升级路径。当前实现的 kalmanFilters 库提供了完整的 IMM 融合（CV+CA+CS / CV+CA+CS+Singer 可选组合），可以同时运行多个运动模型并按似然度加权融合。

关键代码：
- `armor_tracker/` 中的 `kalmanFilters/filters/combined_models/`

### 7. Outpost 前哨站专用 ModeFSM

当前实现有专为前哨站（3 面板）设计的 ModeFSM（AMBIGUOUS ↔ SINGLE_ARMOR 模式切换），以及 OutpostTrilevelJumpDecoder。参考方案没有提及前哨站的特殊处理。

关键代码：
- `max_entropy_tracker/core/mode_fsm.hpp`

## 二、当前实现未考虑到或可以改进的方面

### 1. IMU 四元数 Slerp 插值（时间对齐）

参考方案明确描述了维护 IMU 姿态时间戳队列，通过 Slerp 将 IMU 姿态插值到图像采集时刻。当前实现依赖 `tf2_ros::MessageFilter` 做时间对齐，但没有直接对 IMU 四元数做 Slerp 插值。在相机和 IMU 采样时刻不同步时，坐标系变换存在时间对准误差。

### 2. YPD 球坐标观测噪声建模

参考方案将观测噪声建模放在 Yaw-Pitch-Distance 球坐标中（而非 XYZ 笛卡尔坐标），使 R 矩阵随距离动态变化。当前实现使用对角 XYZ 噪声，三个轴用同一个标量 std，且不随距离变化。参见 `02_5B深度分析.md`。

### 3. 通讯延迟的动态测量与建模

参考方案详细描述了指令链路延迟的测量（平均值、P99、抖动、丢包率），使用软件时间戳和逻辑分析仪。当前实现只有一个静态 `timestamp_offset_` 参数，没有动态延迟估计或抖动建模。

### 4. 基于物理模型的云台前馈控制

参考方案描述了详细的云台单轴动力学建模：转动惯量、粘滞阻尼、库伦摩擦、重力项 → 动力学前馈 + PID 反馈。当前实现的 MPC 计算了加速度指令，但未见基于辨识物理参数（惯量、阻尼系数）的前馈力矩计算。

### 5. 指点锁定机制（操作手介入）

参考方案提到操作手手动选择目标、系统锁定直到丢失的交互模式。当前实现的三种选择策略（MinYawDeviation / StickyMinYawDeviation / PriorityList）都是自动筛选，没有外部手动指点的接口。

### 6. IESEKF 迭代更新

参考方案使用 IESEKF 在更新阶段多次迭代，使线性化点更接近真实后验。当前实现使用 UKF（无迹变换，2 阶精度），但没有迭代更新机制。详细分析见 `02_5B深度分析.md`。

### 7. 散布评估与命中概率建模

参考方案有正式的弹丸散布评估，并用于指导射击阈值判断。当前实现的 FireAdvisor 存在，但未见基于实测散布统计的命中概率量化模型。

## 三、各模块对比速查表

| 模块 | 参考方案核心技术 | 当前实现状态 | 差距 |
|------|-----------------|-------------|------|
| 感知检测 | YOLO-Pose | NN检测器（3后端）+ 传统CV检测器 | 更优 |
| 角点优化 | CornerRefine, PCA | LightCornerCorrector (PCA) + g2o BA | 更优 |
| 位姿解算 | solvePnP, fit_single/double | IPPE PnP + BA yaw优化 | 更优 |
| 目标估计 | KF → EKF → 11D整车EKF | 11D/14D UKF + IMM | 同级/更优 |
| 噪声建模 | YPD球坐标 + Piecewise White Noise | Piecewise White Noise (Q正确), XYZ对角 (R可改进) | R需改进 |
| 匹配关联 | 马氏距离匹配 | 马氏距离门控已实现但默认关闭 | 需启用 |
| 迭代更新 | IESEKF | 无 (UKF单次更新) | 可改进 |
| 时间同步 | IMU Slerp + 时间戳队列 | tf2 MessageFilter | 可改进 |
| 延迟补偿 | process + comm + fly_time | 弹道飞行时间迭代 + DelayAudit | 通讯延迟需加强 |
| MPC控制 | TinyMPC, ADMM | qpOASES MPC（完整实现） | 更优 |
| 云台前馈 | 动力学参数辨识 + 前馈 | MPC加速度指令 | 无物理参数辨识 |
| 多目标 | 加权打分 + 指点锁定 | 3种自动策略 | 缺指点锁定 |

## 四、实施可行性审计修正（基于当前链路）

1. 当前运行主链路为 `bringup_pipeline.launch.py`，`tracker → selector → controller` 已合并为 `gimbal_pipeline` 单节点，实施改动应优先落在 `gimbal_pipeline` 对应代码与参数。
2. 参数生效路径是“包默认 + 机器人覆盖”，不是单一 YAML：
   - 包默认：`rm_auto_aim/gimbal_pipeline/config/gimbal_pipeline.yaml`
   - 机器人覆盖：`rm_bringup/config/<robot>/gimbal_pipeline.yaml`
   - 启动入口默认机器人：`rm_bringup/config/launch_params_decoupled.yaml` 中 `robot: 'leg'`
3. 门控与 Q 参数调优必须按机器人配置分批推进（`leg → hero → infantry_4_1`），避免跨车型参数串扰导致误判。
