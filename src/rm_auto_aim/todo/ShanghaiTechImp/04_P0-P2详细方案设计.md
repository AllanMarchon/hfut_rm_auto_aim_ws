> 基于 `01_整体对比分析.md`、`02_5B深度分析_R矩阵Q矩阵马氏距离IESEKF.md`、`03_改进实施路线图.md`，结合当前 `bringup_pipeline.launch.py` 的真实运行链路，对 P0-P2 给出更细化的实施设计、风险拆解和落地顺序。

## 1. 先校准真实运行链路

### 1.1 当前主入口

当前实测主入口是：

- [bringup_pipeline.launch.py](../../../rm_bringup/launch/bringup_pipeline.launch.py)

它不是旧的解耦链路，而是直接启动统一节点：

- `camera`
- `armor_detector`
- `ballistic_solver`
- `gimbal_pipeline`
- `serial_driver / virtual_serial`

其中 tracker / selector / controller 已经合并进：

- [gimbal_pipeline_node.cpp](../../gimbal_pipeline/src/gimbal_pipeline_node.cpp)

因此，P0-P2 的真实运行落点不是独立 `max_entropy_tracker_node`，而是 `gimbal_pipeline` 内嵌的 tracker 实现。

### 1.2 启动时序与数据流

`bringup_pipeline.launch.py` 的关键时序如下：

1. 读取 [launch_params_decoupled.yaml](../../../rm_bringup/config/launch_params_decoupled.yaml)
2. 根据其中 `robot` 选择机器人覆盖参数目录
3. `1.5s` 启动 `serial`
4. `2.0s` 启动 `ballistic_solver`
5. `2.0s` 启动 `camera + detector`
6. `2.5s` 启动 `gimbal_pipeline`

`gimbal_pipeline` 节点内部数据流为：

1. 订阅 `/armor_detector/armors`
2. 用 `tf2_ros::MessageFilter` 等待该时刻 TF 就绪
3. 内部调用 `TrackerManager`
4. 内部完成目标选择
5. 内部完成控制解算
6. 发布 `cmd_gimbal`
7. 在 launch 中 remap 到 `/armor_solver/cmd_gimbal`

对应代码位置：

- [gimbal_pipeline_node.cpp](../../gimbal_pipeline/src/gimbal_pipeline_node.cpp)
- [bringup_pipeline.launch.py](../../../rm_bringup/launch/bringup_pipeline.launch.py)

### 1.3 参数覆盖顺序

`bringup_pipeline.launch.py` 中 `gimbal_pipeline` 的参数加载顺序是：

1. 包默认：
   - [gimbal_pipeline.yaml](../../gimbal_pipeline/config/gimbal_pipeline.yaml)
2. 机器人覆盖：
   - [leg/gimbal_pipeline.yaml](../../../rm_bringup/config/leg/gimbal_pipeline.yaml)
   - [hero/gimbal_pipeline.yaml](../../../rm_bringup/config/hero/gimbal_pipeline.yaml)
   - [infantry_4_1/gimbal_pipeline.yaml](../../../rm_bringup/config/infantry_4_1/gimbal_pipeline.yaml)
3. launch 额外注入：
   - `debug_mode`

当前默认机器人来自：

- [launch_params_decoupled.yaml](../../../rm_bringup/config/launch_params_decoupled.yaml)

默认值为：

- `robot: 'leg'`

因此，不带额外 launch 参数时，P0-P2 实际生效的是 `leg/gimbal_pipeline.yaml`，不是包默认 YAML。

## 2. 代码落点审计结论

### 2.1 真实实现路径需要修正

`03_改进实施路线图.md` 中部分路径写成了 `src/gimbal_pipeline/...`，但当前仓库真实可运行路径是：

- [src/rm_auto_aim/gimbal_pipeline/include/max_entropy_tracker/core/config.hpp](../../gimbal_pipeline/include/max_entropy_tracker/core/config.hpp)
- [src/rm_auto_aim/gimbal_pipeline/src/max_entropy_tracker/filters/dual_radius_spin_ukf.cpp](../../gimbal_pipeline/src/max_entropy_tracker/filters/dual_radius_spin_ukf.cpp)
- [src/rm_auto_aim/gimbal_pipeline/src/gimbal_pipeline_node.cpp](../../gimbal_pipeline/src/gimbal_pipeline_node.cpp)

仓库里还存在一套独立包实现：

- [src/rm_auto_aim/max_entropy_tracker](../../max_entropy_tracker)

但 `bringup_pipeline.launch.py` 不走这一路。对 P0-P2 来说：

1. 本轮实施对象只保留 `gimbal_pipeline` 内嵌 tracker
2. 本轮不回补独立 `max_entropy_tracker` 包
3. 文档、实现、验证范围统一以 `src/rm_auto_aim/gimbal_pipeline` 为边界

### 2.2 P0 是否可以基于当前实现引入 YPD

结论：可以引入，而且从实现审计看属于低侵入、边界清晰的改动。

原因如下：

1. 单观测 `R` 的构造集中在 [dual_radius_spin_ukf.cpp](../../gimbal_pipeline/src/max_entropy_tracker/filters/dual_radius_spin_ukf.cpp) 的 `update_single()` 内部
2. 当前观测接口已经固定为 `z=[x,y,z,yaw]`，可以直接在该处由 `XYZ` 反算 `YPD`
3. `R` 只参与 `Pzz` 与 Kalman gain 计算，不改变状态维度、观测维度和消息接口
4. 现有 `height_confidence` / `position_confidence` 缩放逻辑可以直接复用，不需要联动修改上层 binder / tracker 语义
5. 双观测路径 `update_dual()` 独立存在，因此 P0 可以只改单观测路径，不会波及双观测几何模型

所以 P0 的判断不只是“理论上可做”，而是“当前实现结构天然支持引入 YPD 单观测噪声建模”。

### 2.3 本轮范围对默认启动链路的影响

虽然本轮文档统一为“仅修改 `src/rm_auto_aim/gimbal_pipeline` 包”，但默认启动链路仍会在包默认 YAML 之上叠加：

- `rm_bringup/config/<robot>/gimbal_pipeline.yaml`

这意味着：

1. 本轮若只改 `gimbal_pipeline/config/gimbal_pipeline.yaml`
2. 默认 `bringup_pipeline.launch.py` 在 `robot=leg` 时
3. 很可能仍会被 `rm_bringup/config/leg/gimbal_pipeline.yaml` 覆盖

因此本轮目标应明确为：

1. 完成 `gimbal_pipeline` 包内代码与默认参数设计
2. 保证包内测试、bag 回放、显式加载包默认参数的路径可验证
3. 暂不承诺“默认 bringup 启动即自动生效”

若后续需要实机默认生效，再单独追加 `rm_bringup` 参数同步。

### 2.4 P2 的一个关键事实

当前 4 板主 UKF 的构造函数中：

- [dual_radius_spin_ukf.cpp](../../gimbal_pipeline/src/max_entropy_tracker/filters/dual_radius_spin_ukf.cpp)

调用的是：

```cpp
return create_default_process_model(
    cfg.motion.translation_model,
    RotationModel::CV, tc, rc, sc, 3);
```

这意味着当前 4 板主链路的旋转模型被硬编码为 `RotationModel::CV`。

直接后果：

1. `spin.spin_process_noise_delta_rate` 生效
2. `spin.spin_process_noise_delta_acc` 对当前 4 板主链路基本不生效
3. `03` 文档里“P2 通过调 `spin_process_noise_delta_acc` 改主跟踪器旋转机动性”的说法，对当前主链路并不成立

`spin.spin_process_noise_delta_acc` 仍可能影响：

1. outpost 分支
2. 其他含 CA 旋转模型的分支
3. 兼容/历史实现

但对 `bringup_pipeline` 当前 4 板主路径，P2 的主调参量应优先看：

1. `motion.singer_sigma`
2. `motion.singer_alpha`
3. `spin.spin_process_noise_delta_rate`

而不是先看 `spin.spin_process_noise_delta_acc`

## 3. P0 详细方案: YPD 球坐标观测噪声建模

## 3.1 当前实现现状

运行时主代码位置：

- [dual_radius_spin_ukf.cpp](../../gimbal_pipeline/src/max_entropy_tracker/filters/dual_radius_spin_ukf.cpp)

当前单观测 `R` 构造逻辑本质上是：

1. `XYZ` 三轴统一使用 `ukf.obs_noise_pos`
2. `yaw` 使用 `ukf.obs_noise_yaw`
3. 初始 `R` 为对角阵
4. `height_confidence` 只放大 `R(2,2)`
5. `position_confidence` 只放大 `R(0,0)` 与 `R(1,1)`

这会带来 4 个问题：

1. `X/Y/Z` 共享同一尺度，不符合 PnP 误差的方向性
2. 噪声与距离无关，远距离目标被过度信任
3. `X/Y` 的相关性被完全忽略
4. 当前不同机器人只能靠非常激进的 `obs_noise_pos` 人工硬顶

从现有配置也能看到这种“硬顶”已经很严重：

| 车型 | `ukf.obs_noise_pos` |
|------|---------------------|
| default | 0.03 |
| leg | 0.003 |
| hero | 0.08 |
| infantry_4_1 | 0.8 |

这说明当前单标量 `obs_noise_pos` 已经被不同车型拿来同时补偿：

1. 相机精度差异
2. 距离尺度差异
3. 观测几何差异
4. 目标机动差异

P0 的意义，是把这些耦合因素里最该由观测模型承担的部分，从“经验调大/调小常数”还原回物理量。

## 3.2 设计目标

P0 不改变 UKF 框架，不改状态维度，不改观测量定义，只替换“单观测 `R` 的构造方式”。

目标是：

1. 保持当前 `z=[x,y,z,yaw]`
2. 保持单观测/双观测更新入口不变
3. 仅把单观测 `R` 从 `XYZ` 固定对角噪声升级为 `YPD -> XYZ` 动态噪声
4. 保留现有 `height_confidence / position_confidence` 缩放逻辑作为第一阶段回归保护

## 3.3 本轮修改边界

本轮只修改：

1. `src/rm_auto_aim/gimbal_pipeline` 下的代码与默认配置
2. 不修改 `src/rm_auto_aim/max_entropy_tracker`
3. 不修改 `rm_bringup/config/<robot>/gimbal_pipeline.yaml`

因此，P0 的最小闭环是：

1. 包内参数结构完成
2. 包内默认 YAML 完成
3. `update_single()` 的 `R` 建模完成
4. 能通过显式加载包默认参数或测试入口验证

## 3.4 建议新增参数

新增到：

- [config.hpp](../../gimbal_pipeline/include/max_entropy_tracker/core/config.hpp)
- [gimbal_pipeline_node.cpp](../../gimbal_pipeline/src/gimbal_pipeline_node.cpp)

建议新增：

```yaml
ukf.ypd_sigma_azi: 0.010
ukf.ypd_sigma_ele: 0.010
ukf.ypd_sigma_dist_coeff: 0.08
ukf.enable_ypd_observation_noise: true
```

说明：

1. `enable_ypd_observation_noise`
   - 第一阶段建议显式开关化
   - 便于 bag A/B 回放与快速回退
2. `ypd_sigma_azi`
   - 方位角标准差，单位 rad
3. `ypd_sigma_ele`
   - 俯仰角标准差，单位 rad
4. `ypd_sigma_dist_coeff`
   - 距离噪声系数，`sigma_dist = coeff * range`

不建议一上来删除：

- `ukf.obs_noise_pos`

建议保留为 fallback，并兼容旧参数。

## 3.5 推荐实现方式

### 方案原则

第一阶段应优先“低侵入、可回退”，因此推荐：

1. 用当前预测观测 `z_pred.head<3>()` 计算雅可比
2. 当 `range` 或 `range_xy` 太小、数值不稳定时回退旧 `R`
3. 先保留原有 `height_confidence / position_confidence` 的后置放大
4. 双观测 `R_geo` 暂不改

推荐用预测观测而不是原始观测来计算雅可比，原因是：

1. 对异常测量更稳
2. 不会让离群点直接参与 `R` 尺度构造
3. 与 gating 的“先预测再判别”逻辑更一致

### 推荐公式

记：

1. `azi = atan2(y, x)`
2. `ele = atan2(z, sqrt(x^2+y^2))`
3. `dist = sqrt(x^2+y^2+z^2)`

球坐标噪声：

```text
R_ypd = diag(
  sigma_azi^2,
  sigma_ele^2,
  (sigma_dist_coeff * dist)^2,
  sigma_yaw^2
)
```

再通过雅可比变换到 `XYZyaw`：

```text
R = J * R_ypd * J^T
```

其中：

```text
x = dist * cos(ele) * cos(azi)
y = dist * cos(ele) * sin(azi)
z = dist * sin(ele)
```

### 置信度缩放建议

第一阶段不要改动现有置信度语义，保持：

1. `height_confidence < 0.3` 时放大 `R(2,2)`
2. `position_confidence < 0.8` 时放大 `R(0,0)`、`R(1,1)`

理由：

1. 这部分已经和上层 height/binder 逻辑耦合
2. 若同时改 `R` 主体和置信度缩放语义，回归定位会变难

第二阶段若效果稳定，再考虑把置信度缩放前移到 `YPD` 域。

## 4. P1 详细方案: 启用马氏距离门控

## 4.1 当前实现现状

主实现位置：

- [dual_radius_spin_ukf.cpp](../../gimbal_pipeline/src/max_entropy_tracker/filters/dual_radius_spin_ukf.cpp)

当前已经有完整 gate：

1. `yaw` 按 1 自由度卡方
2. `position` 按 3 自由度卡方
3. 判定逻辑是 `yaw_pass || pos_pass`

默认参数：

```yaml
ukf.enable_innovation_gating: false
ukf.innovation_gate_chi2_threshold: 9.49
```

`9.49` 更接近 1 自由度很严格的门限配置，且当前 `R` 又不准确，所以默认关闭是合理历史结果。

## 4.2 一个必须写入方案的实现风险

当前 `AdaptiveArmorTracker::update()` 的顺序是：

1. `handle_observation_received(...)`
2. 再调用 `ukf_.update(...)`

对应代码：

- [adaptive_armor_tracker.cpp](../../gimbal_pipeline/src/max_entropy_tracker/trackers/adaptive_armor_tracker.cpp)

这意味着：

1. 只要本帧有 detector 观测，`lost_count` 就会被清零
2. 即使 `ukf_.update()` 因 gate 拒绝返回 `false`
3. tracker 也不会因为这次拒绝立刻进入 `TEMP_LOST`

所以，`03` 文档里“连续多帧被拒绝时状态机应转入 TEMP_LOST”这句话，在当前代码下并不会自然发生。

这是 P1 最大的链路级风险。

## 4.3 推荐实施方式

P1 建议拆成两个子阶段。

### P1-A 先做观测统计，不改变状态机

先只启用 gate 与统计：

1. `enable_innovation_gating: true`
2. 记录：
   - gate 总判定次数
   - reject 次数
   - `chi2_yaw`
   - `chi2_pos`
   - `last_nis`
3. 每 100 帧或每 1s 节流输出一次统计

推荐先只在 `leg` 打开。

这样能先回答两个问题：

1. P0 之后 gate 是否已有足够区分度
2. reject 比例是否处在可接受范围

### P1-B 再补“拒绝观测如何影响状态机”

推荐新增“门控拒绝 streak”机制，而不是直接改成“只要 gate 失败就 lost”。

建议行为：

1. 单帧 gate reject
   - 仅跳过本次 UKF 更新
   - tracker 保持 TRACKING
2. 连续 `N` 帧 gate reject
   - 视为“伪缺失观测”
   - 对 tracker 触发一次 `handle_observation_loss(...)`
3. gate 一旦恢复通过
   - 清空 reject streak

建议新增参数：

```yaml
ukf.gate_reject_streak_to_temp_lost: 3
ukf.gate_debug_log_enable: true
```

这样可以避免：

1. 单次异常检测导致频繁闪断
2. 长时间被错误观测“保活”而状态机却不降级

## 4.4 阈值设计建议

如果 P0 已落地，P1 的初始阈值建议：

1. `leg`: 6.0 左右起步
2. `hero`: 6.0 到 8.0
3. `infantry_4_1`: 先不要直接复用，必须先看 P0 后的 NIS

不建议一上来全车型统一用一个阈值，原因是当前三份机器人配置差异过大：

| 车型 | `ukf.obs_noise_pos` | `motion.singer_sigma` |
|------|----------------------|-----------------------|
| leg | 0.003 | 0.8 |
| hero | 0.08 | 0.30 |
| infantry_4_1 | 0.8 | 15.0 |

在 P0 完成前，这些配置背后的统计尺度并不统一。

## 4.5 需要修改的文件

本轮最小建议改动集：

1. [config.hpp](../../gimbal_pipeline/include/max_entropy_tracker/core/config.hpp)
2. [gimbal_pipeline_node.cpp](../../gimbal_pipeline/src/gimbal_pipeline_node.cpp)
3. [dual_radius_spin_ukf.hpp](../../gimbal_pipeline/include/max_entropy_tracker/filters/dual_radius_spin_ukf.hpp)
4. [dual_radius_spin_ukf.cpp](../../gimbal_pipeline/src/max_entropy_tracker/filters/dual_radius_spin_ukf.cpp)

## 4.6 验证与验收

验收不应该只看“有没有 reject”，还要看 reject 之后系统是否健康。

建议指标：

1. reject ratio：目标 `2% - 8%`
2. 连续 reject streak 分布
3. gate reject 后的追踪恢复时间
4. stale tracking 是否下降
5. `TEMP_LOST` / `LOST` 触发频率是否异常升高

## 5. P2 详细方案: Q 矩阵参数重标定

## 5.1 当前现状与 `03` 路线图的差异

`03` 文档把 P2 理解为：

1. 提高 `motion.singer_sigma`
2. 适当降低 `spin.spin_process_noise_delta_acc`

但按当前主运行链路审计，P2 需要修正为：

1. 平移机动性主要由 `motion.singer_sigma` / `motion.singer_alpha` 决定
2. 旋转机动性主要由 `spin.spin_process_noise_delta_rate` 决定
3. `spin.spin_process_noise_delta_acc` 对当前 4 板主链路不是主调参量

这意味着 P2 不能按 `03` 的说法直接推进，否则会出现：

1. 改了参数
2. 主链路几乎没变化
3. 误判为“Q 调参无效”

## 5.2 当前三车型参数已经高度分化

包默认与当前主链路相关配置现状：

| 车型 | `motion.singer_alpha` | `motion.singer_sigma` | `spin.spin_process_noise_delta_rate` |
|------|------------------------|------------------------|--------------------------------------|
| default | 0.8 | 0.5 | 3.50 |
| leg | 1.8 | 0.8 | 3.25 |
| hero | 1.5 | 0.30 | 3.50 |
| infantry_4_1 | 10.5 | 15.0 | 3.50 |

这里能看出一个重要结论：

1. `infantry_4_1` 不是“Q 偏小”，而是已经非常激进
2. `hero` 才是明显偏保守的候选
3. `leg` 处于中间态

因此，P2 不是“统一调大 Q”，而是“按车型重新做机动能力分层”。

## 5.3 建议分成两条调参主线

### 主线 A: 平移机动性

核心参数：

1. `motion.singer_sigma`
2. `motion.singer_alpha`

建议理解为：

1. `sigma` 决定允许多大机动加速度
2. `alpha` 决定机动加速度衰减速度

建议初步方向：

| 车型 | 建议方向 |
|------|----------|
| leg | `0.8 -> 1.2~2.0` |
| hero | `0.3 -> 1.0~2.5` |
| infantry_4_1 | 先不继续增大，先回放确认是否已过激 |

### 主线 B: 旋转机动性

当前 4 板主路径应优先调：

1. `spin.spin_process_noise_delta_rate`

建议范围：

| 车型 | 建议方向 |
|------|----------|
| leg | `3.25 -> 3.5~5.0` |
| hero | `3.50 -> 4.0~5.5` |
| infantry_4_1 | 先维持，观察 gate 后的旋转预测残差 |

## 5.4 推荐调参顺序

P2 不建议在 P0/P1 前做。推荐顺序：

1. 先完成 P0，让 `R` 尺度合理
2. 再完成 P1-A，拿到 `NIS / reject` 统计
3. 最后做 P2，对“预测太硬还是观测太硬”做区分

否则容易把 `R` 错配造成的创新异常，误调到 `Q` 上。

## 5.5 推荐验证维度

P2 不应只看视觉轨迹，还要看控制输出与机动检测。

建议同步观察：

1. `last_nis`
2. 位置创新范数
3. `delta_rate` 跟随滞后
4. 云台指令抖动频率
5. `maneuver_states` 调试话题

验收建议：

1. 大机动时角度峰值误差下降
2. 连续转向时不出现明显追踪拖尾
3. 控制输出无新增高频抖动
4. `reject ratio` 不因 Q 调大而大幅恶化

## 7. 最终建议结论

### 7.1 P0 是最高优先级且收益最确定的改动

它只改观测噪声构造，不改状态结构，风险最可控，同时还能为 P1/P2 提供正确统计基础。

### 7.2 P1 不能只改 YAML

如果只把 `enable_innovation_gating` 打开，而不处理“gate reject 不驱动状态机降级”的问题，就会出现：

1. UKF 不更新
2. tracker 仍保持 TRACKING
3. 系统被坏观测持续保活

所以 P1 至少应分成“统计上线”和“状态机联动”两个阶段。

### 7.3 P2 不能按原路线图机械推进

当前主运行链路下，`spin.spin_process_noise_delta_acc` 不是 4 板主跟踪器的主要生效参数。P2 应优先围绕：

1. `motion.singer_sigma`
2. `motion.singer_alpha`
3. `spin.spin_process_noise_delta_rate`

重做车型化标定。

### 7.4 推荐的一句话版本

推荐把本轮改造定义为：

1. 先在 `src/rm_auto_aim/gimbal_pipeline` 内完成 P0，把观测噪声模型从“常数 R”升级为“距离相关 R”
2. 再在同一包内完成 P1，把已有 gate 从“代码存在”升级为“统计可观测、状态机可联动”
3. 最后在同一包内完成 P2 的主链路 Q 标定
4. 旧实现与 `rm_bringup` 机器人覆盖参数同步，放到下一阶段单独处理
